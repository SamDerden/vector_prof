# OOD мастерской «Вектора»: пилот и первый эксперимент

Мы проверяем, относится ли вопрос к профессиональному ориентированию. Это отдельная задача от проверки безопасности, достоверности ответа и достаточности базы знаний. Вопрос о проходном балле релевантен, даже если свежего балла в каталоге нет. Короткий вопрос «А сколько учиться?» нельзя автоматически отклонять.

## Что мы сделали 27 ноября 2026

Мы прочитали актуальный `backend/data/export/navigator.json`: 152 профессии. SHA-256, список ID и покрытие сохранены в `inventory.json`. Запросить большой JSON через GitHub API больше не требуется: он доступен в checkout.

В `annotation_matrix.json` описаны три класса и оси проверки. Создали пилот `pilot.jsonl`: 200 relevant, 150 out_of_domain, 150 needs_clarification. Для каждой строки сохранены профессия, класс, намерение, происхождение, выборка и статус проверки. Все 500 меток имеют `review_status=pending`. Мы не выдаём эти строки за реальные вопросы школьников или подтверждённую экспертами разметку.

Пилот содержит **50 намерений по 10 вариантов вводной фразы**. Это только 50 независимых смысловых групп, а не 500 независимых наблюдений. Контекстные ID покрывают 152 профессии, но вопросы общие: это не глубокое предметное покрытие каждой профессии. История диалога пока пустая. Нужны самостоятельные примеры с историей, опечатками, смешанными намерениями и сложными границами.

## Разбиение и утечки

Сначала мы назначаем train/validation/test целым намерениям, затем создаём варианты. Близкие варианты одного шаблона не попадают в разные выборки. Получилось 380/60/60 строк. Проверяем нормализованные точные дубли и пересечение `intent_group`. Тематические пересечения между разными намерениями требуют ручного аудита; автоматический контроль не доказывает отсутствие всех смысловых утечек. Отдельный `challenge.json` содержит 30 вручную составленных автором примеров, не участвующих в обучении. Его метки также требуют независимого ревью. После просмотра ошибок этот набор нельзя использовать для подбора модели и продолжать называть нетронутым финальным тестом.

## Эксперимент

Мы обучили char TF-IDF, n-gram 3–5, sublinear TF, и LogisticRegression с балансировкой классов, seed 27, max_iter 1000. Векторизатор обучается только на train. Входом служит вопрос; возраст, профессия и история не используются этой базовой моделью. Параметры не подбирались по тесту. Результат и ошибки сохранены в `baseline-report.json`:

| Выборка | Строк | Macro-F1 |
|---|---:|---:|
| Validation | 60 | 0,719 |
| Test по новым намерениям | 60 | 0,627 |
| Challenge | 30 | 0,795 |

На Challenge один из 12 релевантных вопросов не распознан как relevant. В отчёте отдельно приведены доля жёстких ложных отклонений (`out_of_domain`) и доля всех пропусков relevant, confusion matrix, precision/recall/F1 по классам и p50/p95 времени одиночного предсказания. Latency измерена на этой машине и не является серверным SLA.

## Воспроизведение

Из корня репозитория:

```bash
python -m pip install -r ml/ood/requirements.txt
python ml/ood/build_pilot.py
python ml/ood/evaluate.py
```

Можно открыть `baseline.ipynb`. Генератор перезаписывает только синтетический пилот и инвентаризацию; разметку экспертов нужно хранить отдельно, не редактировать генерируемый файл. Сам эксперимент не обращается к шлюзу, не передаёт данные школьников и не меняет runtime-фильтр. Экспериментальный объект сохранён в artifacts; в приложение он не загружается.

## Что остаётся

1. Два независимых разметчика проверяют пилот и Challenge; разногласия разрешаются с фиксацией причины. Согласовать определения классов с системным аналитиком и AI-лидом.
2. Расширить независимые намерения, собрать вопросы с историей и по конкретным профессиям, возрастам и отраслям; провести содержательную дедупликацию и проверить покрытие.
3. После приёмки пилота сформировать основной датасет. Размер и распределение определять по покрытию, не только по числу строк.
4. Сравнить embeddings + классификатор и LLM на одинаковых утверждённых выборках. Сейчас эти эксперименты не запускались: нужен согласованный шлюз и доступ.
5. Отдельно провести adversarial-проверки, prompt injection и модерацию. OOD их не заменяет.
6. Установить пороги допуска, измерить ошибки и задержки на целевом окружении, затем принимать решение о подключении. Текущая модель не готова к production и не включена в мастерскую.
