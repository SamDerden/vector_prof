# Preflight перед production

Этот чеклист описывает локально подготовленные шаги. Он не заменяет проверку на целевом окружении и не разрешает deploy.

## Что уже можно сделать локально

- Каталог freeze читается в runtime: 152 профессии, 184 пробы, 337 программ.
- Пустая таблица `professions` больше не даёт 503, если freeze доступен. Профессия без UUID отдаётся по стабильному `profession_id`.
- Синхронизация профессий добавляет недостающие строки и не удаляет существующие. UUID создаёт только PostgreSQL. Повторный запуск не создаёт дубли.
- Сборщик эмбеддингов читает freeze. `--dry-run` не ходит в сеть. Semantic включается только для проверенного индекса `vector_source=provider` на все 152 профессии. Текущий индекс EmbeddingsGigaR остаётся лексическим fallback и не заменяется mock-векторами.
- Доставка кодов регистрации, повторного подтверждения, сброса пароля и входа по коду идёт через один SMTP/HTTP/file транспорт. В production регистрация остаётся выключенной, пока доставка не проверена на целевом окружении.

## Изолированная база

Разрешено подключаться только к `127.0.0.1:55432` пользователем изолированного стенда.

Не использовать:

- `navigator-postgres` на порту 5433;
- рабочую базу `vector_prof_generation_stand`;
- production, Railway и любые другие хосты.

Новая чистая база для миграций: имя `vector_prof_migration_*`.
Клон с тестовыми данными: имя `vector_prof_sync_*`.
Миграции 001–012 не изменяются. Синхронизация профессий не добавляет свою миграцию и использует уже существующие колонки. Коды входа требуют `013_login_codes.sql`: она только расширяет допустимые значения `auth_challenges.purpose` до `verify`, `reset`, `login`.

На `origin/main` после закрытия PR #15 есть другой файл, `013_pm_features.sql` (мастерская, отзывы, PDF). В эту ветку он не переносился. Имена файлов не совпадают, но оба имеют номер 013. Перед общим применением на одной базе нужен согласованный порядок, без перезаписи уже применённых миграций и без деплоя из этой ветки.

Команда синхронизации из каталога `backend`:

```text
node --experimental-strip-types scripts/sync-freeze-professions.mjs
node --experimental-strip-types scripts/sync-freeze-professions.mjs --apply
```

`--apply` требует `CONFIRM_FREEZE_SYNC=data_freeze_1`. Для чистой базы `vector_prof_clean_20261125` дополнительно нужен `CONFIRM_FREEZE_SYNC_DATABASE` с её точным именем. Рабочий стенд команда отклоняет.

## Откат

Автоматического отката, который удаляет аккаунты или профессии, нет. Перед применением на целевой базе снять логический backup. Если миграция или синхронизация не прошла, восстановить этот backup. Не выполнять `DROP`, `DELETE` или `TRUNCATE` по пользовательским таблицам как способ отката.

## Семантический индекс

Проверка без сети:

```text
node --experimental-strip-types scripts/build-embedding-index.mjs --dry-run
```

Реальные векторы строить только отдельной командой, когда есть непроизводственный шлюз EmbeddingsGigaR на 2560 измерений:

```text
node --experimental-strip-types scripts/build-embedding-index.mjs --apply
```

Пока такой индекс не проверен, retrieval остаётся на лексическом fallback. Mock-файл нельзя записывать поверх `data/catalog.index.json`.

## Почта

Локальная проверка Mail.ru уже выполнена раньше и в этом проходе не повторялась: новые письма не отправлялись. Пользователь подтвердил доставку всех четырёх писем на `SMTP_TEST_TO`:

1. регистрация;
2. повторная отправка подтверждения;
3. восстановление пароля;
4. вход по одноразовому коду.

Транспорт один и тот же: `AUTH_EMAIL_TRANSPORT=smtp`, хост Mail.ru, порт 465, `SMTP_SECURE=true` (TLS с первого пакета, не STARTTLS на 587). Пароль внешнего приложения и `AUTH_CHALLENGE_SECRET` остаются только в локальном `backend/.env.smtp-test.local`. Этот файл в `.gitignore` и не входит в коммиты. Код не пишется в JSON ответа API, в обычный лог ошибки и в cookie. В письме и во внутреннем вызове транспорта код есть, потому что иначе письмо нечего доставлять.

Повторная отправка подтверждения и запрос кода входа ограничены одним запросом в 60 секунд. Запрос сброса пароля ограничен пятью обращениями в час. TTL кода — 900 секунд. Пять неверных попыток блокируют код. Новый код погашает предыдущий. Ответы на неизвестный адрес остаются нейтральными. Конкурентное погашение на PostgreSQL делает блокировку строки, условный `UPDATE` и создание сессии в одной транзакции. Сегодня изолированный PostgreSQL на `127.0.0.1:55432` не слушает порт, поэтому этот проход не повторял ни dry-run синхронизации, ни конкурентный тест. Ранее они проходили на временной базе; это не сегодняшняя проверка.

### Конфигурация для VDS, без подключения и без включения

Не применять эти значения на VDS из этого изменения. Регистрация в production остаётся выключенной.

Переменные окружения, значения секретов задаются только на сервере:

- `AUTH_CHALLENGE_SECRET` — отдельный длинный секрет, не равен паролю SMTP;
- `AUTH_EMAIL_TRANSPORT=smtp`;
- `SMTP_HOST=smtp.mail.ru`;
- `SMTP_PORT=465`;
- `SMTP_SECURE=true`;
- `SMTP_USER` и `SMTP_FROM` — технический ящик;
- `SMTP_PASSWORD` — пароль внешнего приложения Mail.ru;
- `AUTH_REGISTRATION_ENABLED=false`, пока проверка ниже не пройдена на самом VDS.

Проверка подключения без письма: из каталога `backend` запустить `node --experimental-strip-types scripts/smtp-mailru-test.mjs` с локальным env-файлом вне Git. Команда без `--send` только проверяет план транспорта и не соединяется с сервером. Реальную отправку (`--send`) делать отдельным разрешённым окном и не из этого прохода.

Включать регистрацию только после успешной доставки на VDS: выставить `AUTH_REGISTRATION_ENABLED=true`. Пока флаг не `true`, production не открывает регистрацию. Если SMTP ответил ошибкой авторизации, TLS или лимитом, вернуть `AUTH_REGISTRATION_ENABLED=false`. Код при этом считает регистрацию ненастроенной и отвечает `503 registration_not_configured`, не создавая новый обходной транспорт.

## Самостоятельные профпробы

BE-05 не выполнен. В freeze есть 42 записи `self_guided_steps` и 42 связи `profession_first_steps`. У шага есть отдельные тексты `grade_5_8_task` и `grade_9_11_task`. Это авторские сценарии каталога, не 184 внешние пробы `trials`.

Runtime читает профессии, пробы и программы через `loadRuntimeCatalog()` и эти 42 шага в API не отдаёт. Нет контракта, который выбирает шаг по профессии и классу и добавляет его в индивидуальный маршрут. Содержимое заданий не дописывалось. Дальше нужен владелец данных: подтвердить, что эти 42 шага и есть утверждённые самостоятельные профпробы, и отдельно согласовать API маршрута.

## Что остаётся перед deploy

- Настроить SMTP на VDS отдельно. Не копировать локальный env-файл в Git и не включать регистрацию до проверки доставки на самом VDS.
- Не сливать эту ветку в `main` из этого прохода. На `origin/main` уже есть три коммита после `d38bd15`: мастерская, PDF, отзывы и OOD. Возможные пересечения: `backend/.env.example`, `backend/package.json`, `backend/lib/ai/retrieval.ts`, `backend/lib/ai/freeze-embedding.ts`, workflow CI и номер миграции 013.
- Прогнать миграции, включая `013_login_codes.sql`, и синхронизацию профессий на копии целевой базы. Сегодняшний стенд `127.0.0.1:55432` был недоступен.
- Построить и проверить provider-индекс EmbeddingsGigaR. До этого semantic не включать.
- Снять backup целевой базы и согласовать окно применения.
- Не считать BE-05 готовым, пока нет утверждённого контракта маршрута для самостоятельных шагов.
